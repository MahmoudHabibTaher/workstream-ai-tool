## Proposed decisions

### P1: a held launch draws as text with its message, since the surface's Button has no disabled state
A probe test rendered `<Button disabled isDisabled>`: the harness kept only `key` and `label` in its props, and a press still fired the handler. So "disables the button" is done by drawing the launch as dimmed text, "Run (blocked: <first blocking message>)", with a **Check again** button under the pre-flight results. Rejected: a Button whose press does nothing, which looks pressable.

### P2: run-task's prompt comes from `ws launch argv --agent claude-code`, the last argument
The snapshot's `launches` are a row's (jetbrains_ux D010), so it holds no run-task text, and `src/workstream` is out of scope. `ws launch argv` is the CLI's own builder of that prompt; the JetBrains plugin reads it the same way. The agent is `claude-code`, the one the pane runs inside. It is fetched only after the checks pass. Rejected: a run-task template in the pane, which PX-01 just removed. **Open.** A `launches` list on each snapshot task would let the pane read it as it reads a row's; that is a src/workstream change for the owner to weigh.

### P3: the pre-flight shows where it was asked, and is cleared on opening a workstream
One `preflight` atom holds the last result with its ws, kind and task. Detail shows a row launch's; the task page shows that task's Run This Task. A held button stays held until **Check again** or opening the workstream afresh, rather than re-checking on every snapshot poll. Rejected: re-running the checks on each poll, which would be a `ws launch check` per launch every 3 seconds.

### P4: Run This Task is offered for a task not done or deferred, in a workstream whose row has launches
That matches where the row's own launches are offered (open rows only). Rejected: offering it on every task.
