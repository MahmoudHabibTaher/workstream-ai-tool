## Proposed decisions

### D007: the capture entry is committed in the "adopt ws" commit, goes before the generated entry, and only the `hook` scenario installs it
It comes first, so it sees every call even where the generated hook denies one and the agent stops there. It copies the generated entry's matcher, so it sees exactly what `ws hook pre-edit` sees. It is committed so the scratch tree starts clean. It is scoped to the `hook` scenario (`Scenario.capture`), so no other scenario's setup changes. One side effect: on Copilot, `.github/hooks/ws.json` no longer matches what `ws adapt` wrote, so `ws doctor` / `file_states` in that scratch repo would call it EDITED. Rejected: a separate capture file under `.github/hooks/` (the brief names ws.json); capturing in every real scenario (outside the scope rule).

### D008: payloads are stored one JSON string per line, outside the repo (`<scratch base>/hook-payloads.jsonl`)
This keeps each raw payload byte for byte, even when it is multi-line or not valid JSON, and `hook.decide` is given that exact raw text. The check counts a payload as "naming" PROGRESS.md the way `hook.decide` does: `hook.paths_in`, resolved against the payload's `cwd`. Rejected: re-serialising parsed payloads, which would lose what was actually sent.

## Gotchas and follow-ups

- The check reports changes on trunk ahead of changes in the working tree. An agent that edited the file but didn't commit gets "in the working tree".
- Whether Copilot runs the capture entry with a `bash` key and empty stdout as an allow is assumed from the generated entry's shape. CF-05's real run will show it.
