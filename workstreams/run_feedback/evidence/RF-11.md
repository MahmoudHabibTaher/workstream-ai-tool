## Proposed decisions

### P1: `ws update --commit` takes an optional value

`ws update` already has `--commit <hash>`, which records a landed commit, and D-ACCEPT wants `--commit` to commit the queue. So a bare `--commit` commits the queue and is accepted only with `--acceptance`; a hash with `--acceptance`, or a bare one without it, is refused. Existing `--commit <hash>` calls behave as before.

Rejected: a differently named flag, since D-ACCEPT and the acceptance name `--commit`.

### P2: `--acceptance` goes alone

Combining it with `--status`, `--notes` or another change is refused, so a call can't both correct an item and mark the task done, and `--commit` commits one change with a message that describes it.

Rejected: letting it combine with the other flags, which makes the done-task refusal depend on the order they apply in.

### P3: the commit helper sits in `cli.py`, not `act.py`

`act.py` isn't in the task's files, and `check_checkout`, `commit` and `restore` are already public there, so the step composes them in `cli.py`.

Rejected: an `act.commit_acceptance` beside `commit_decision`, which matches the pattern better but goes outside the listed files.

## Gotchas and follow-ups

- A bare `ws update --commit <id>` now takes the id as the hash, then argparse refuses the missing id. Only that order is affected.
- The test imports `fill_in` from `tests/test_protocol.py`, so running `tests.test_tasks` also loads that module.
- `--acceptance` checks the decision in the current checkout's `DECISIONS.md` and writes the current checkout's queue, like the rest of `ws update`. From a worktree without `--commit` it would change that worktree's copy, which the brief doesn't read. With `--commit` the integration-branch check refuses it.
- A second correction names only the later decision, because the whole text is replaced. The earlier one stays in git history and the decision log.
