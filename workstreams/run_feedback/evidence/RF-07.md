## Proposed decisions

### P1: `_at_task` returns the opened checkout's registry row, not the integration checkout's

The folder paths in the returned row must fit the checkout that will write evidence, and a row changed on the integration branch since the claim might not. Only the task itself comes from the integration checkout, as D-SOURCE says. Rejected: returning the integration checkout's row, which is simpler but could point a worktree's evidence at a path its branch doesn't have.

## Gotchas and follow-ups

- A workstream that exists only on a side branch can't be briefed or verified while another checkout is on the integration branch. `ws new` doesn't require the integration branch, so this can arise. From a linked checkout on `feature`, I got `error: no workstream with id 'gamma' (see `ws list --all`)` from `ws brief` after `ws new gamma` there. Before this change it read that checkout's registry. Claimed tasks aren't affected, since a claim has to be on the integration branch. Not worked around, because D-SOURCE says everything the brief reads comes from the integration checkout. A fallback for a workstream the integration checkout doesn't have would be small if this matters.
- From a worktree with no `-w`, the "only open workstream" fallback now counts the integration checkout's open workstreams. One opened since the claim gives a "several open" refusal rather than a guess. Briefs always pass `-w`, so workers don't hit it.
- `ws decisions` still reads the current checkout, so from a worktree it misses decisions made since the claim, including the "N more" a brief points to with `ws decisions --for`. Outside this task's issue as written.
- `ws verify` still reads `[commands]` and baselines from the worktree: the task's list is current, but what a key expands to is as of the claim. From reading the code, not run: a command key added to the config on the integration branch after the claim shows in the brief, but the worktree's config doesn't have it when verify runs.
