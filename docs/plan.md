The approved plan for this tool, kept as written. Why it looks like this: [harness-comparison.md](harness-comparison.md). Decisions made with the owner: Python stdlib core, VS Code before JetBrains, Claude Code and Copilot CLI for v1, private repo for now.

## Design principles

1. **The CLI enforces, prompts don't repeat.** A rule the CLI can enforce is removed from prose. This is the main source of context savings.
2. **The CLI assembles context.** Agents ask for what their role needs (`ws brief`) instead of reading files and deciding what matters.
3. **One versioned protocol, never copied.** A workstream pins a version and keeps only what is specific to it.
4. **No project or agent facts in core.** Stack facts go in config, agent facts in generated adapters.
5. **One writer, many views.** Every UI draws `ws snapshot` and writes only through `ws act`. UIs decide nothing.
6. **Budgets are tested.** Context limits fail CI, so prompts cannot quietly regrow.

## Architecture

```
Surfaces    Claude Code mod │ Web UI (browser) │ VS Code │ JetBrains
                    └───────── ws snapshot / act / review ────────┘
Adapters    Claude Code plugin │ Copilot CLI skills        (generated by ws adapt)
Protocol    PROTOCOL.md + skills: ws-plan, ws-run, ws-coordinate, ws-review
Project     .workstream/config.toml + profiles             (written by ws init)
Core        ws CLI: state, graph, gates, verify, brief, settle, audit
State       workstreams/<id>/  committed files + JSON Schema
```

**The key UI decision:** one web UI serves the browser, the VS Code webview and the JetBrains JCEF panel, so each IDE plugin stays a thin wrapper. The Claude Code mod is the exception because mods render their own components. It is already built, so it gets ported rather than rewritten.

## New capabilities neither harness has

| Capability | Replaces | Benefit |
|---|---|---|
| **`ws verify <task>`** runs the commands itself and records exit codes against the tree hash | the Kotlin harness's `--validated` honesty flag, subsonic's self-quoted output | Pass/fail is a recorded fact, not an agent's claim |
| **Bounded output** in `ws verify`: full log to a gitignored file, only the verdict, new findings and a short tail to the agent | Raw Gradle/cargo logs in context | Cuts a cost both harnesses pay on every run |
| **`ws brief <task> --role worker`** renders task, relevant traps and decisions, rules and commands | Hand-written 5.7k-char briefs | The spawn prompt becomes one line: "Run `ws brief X` and follow it" |
| **`ws settle <task>`** checks evidence, records the merge, numbers decisions, updates `PROGRESS` and registry, makes one commit | ~40 lines of manual steps in `dispatch-tasks` Step 4 | Clerical work leaves the orchestrator's context |
| **`ws seed --from-plan`** extracts tasks and plan body from the approved plan | Writing the whole plan twice | Saves 20–35 KB of repeated output |
| **`ws decisions --for <task>`** filters by trap and file overlap | Reading all of `DECISIONS.md` | Targeted reads |
| **`ws audit context`** computes per-role load and fails over budget; **`ws audit usage`** reads transcripts | This manual analysis | Keeps the savings over time |
| **Pluggable baseline parsers**: regex, SARIF, JUnit | Detekt-only parser | Works on any stack |
| **Tiers**: `lite` (plan, tasks, evidence), `standard`, `full` (adds release) | One heavy process for all sizes | Small work stays cheap |

## Layout

Repo root: `<repo root>` (empty today; needs `git init`).

```
src/workstream/   cli, state, schema, graph, gates, verify, baseline, worktree,
                  brief, settle, snapshot, act, review, init, adapt, audit, serve
schema/           JSON Schemas (tasks, registry, config, snapshot)
src/workstream/assets/   PROTOCOL.md, addressable by section via `ws protocol <section>`,
                  and skills/: ws-plan, ws-run, ws-coordinate, ws-review (capability-worded source)
profiles/         cargo, gradle-kmp, node, python, go, generic
adapters/         claude-code (plugin, ws-worker agent, hooks), copilot-cli
ui/               mod, web, vscode, jetbrains
tests/  fixtures/ docs/
```

Each adopting project gets `.workstream/config.toml` plus `workstreams/`:

```toml
schema = 1
[branches]
integration = "develop"          # trunk-based: integration = production = "main"
production  = "main"
task        = "task/{slug}"
merge       = "no-ff"            # no-ff | squash | pr
[commands]
compile = "./gradlew :app:compileKotlin"
test    = "./gradlew :app:test"
lint    = "./gradlew detekt"
check   = "make check"
[baseline.lint]
parser = "regex"                 # regex | sarif | junit | exit-code
[adequacy]                       # enforced by ws validate
declarations = ["compile"]
behaviour    = ["compile", "test"]
tests        = ["test"]
[worktree]
setup = ["ln -s {main}/frontend/node_modules frontend/node_modules"]
[parallel]
max_workers = 3
[release]
mode = "none"                    # none | runbook
runbook = "docs/git-workflow.md#releases"
```

## Commands

| Group | Commands |
|---|---|
| Setup | `init`, `doctor`, `adapt`, `import` |
| Planning | `new`, `seed --from-plan`, `validate`, `baseline record` |
| Running | `wave`, `next`, `brief`, `claim`, `unclaim`, `worktree create\|remove`, `verify`, `evidence check`, `settle`, `handoff` |
| Reading | `status`, `show`, `graph`, `decisions --for`, `protocol <section>` |
| UI contract | `snapshot`, `act`, `review`, `serve` |
| Lifecycle | `set-status`, `close`, `reset` |
| Budgets | `audit context`, `audit usage` |

**`ws init`** detects the stack from marker files, proposes commands from a profile, **runs them on a clean tree** and records the baseline. A command is never written to config unverified. This is the Kotlin harness's Step 2b made automatic.

**Task schema v3** merges both: `id, title, phase, priority, status, kind, blockedBy, files, acceptance[], verify[], mode, requires, releaseImpact, findings, notes`, plus runtime fields written only by the CLI. `verify` holds named command keys, or a raw command where a task needs one.

## Context budgets

Budgets cover only what the harness adds. They exclude the agent's own system prompt, tool definitions and the project's own instructions file.

| Role | subsonic today | the Kotlin harness today | Target |
|---|---|---|---|
| Always-on | ~150 | ~8,800 | **≤ 150** (one pointer + 4 short skill descriptions) |
| Worker orientation | 13–15k | 21–27k | **≤ 2.5k** + cited plan sections |
| Orchestrator static | ~12k | ~14k | **≤ 3k** |
| Orchestrator per task | ~2.5k + bookkeeping | ~1.6k | **≤ 400** |
| Planner | ~9k | ~14k | **≤ 3k** + schema on demand |

**Pilot success measures (subsonic):** worker growth from turn 1 to turn 5 falls from about 26k to ≤ 8k, and orchestrator peak falls from about 163k to ≤ 80k on comparable work. These are targets, not predictions. The 54k baseline at turn 1 is mostly outside this tool's control. A `ws-worker` agent with only the tools it needs might reduce it, and the pilot will test that.

## Boundaries

- **the Kotlin harness is shared with your team and is a work project.** Nothing is pushed there, and no the Kotlin harness content enters this repo: fixtures are synthetic, and replay tests read the local checkout and skip when it is absent. Adopting the tool there is a separate decision for you and your team. This also keeps a future public release clean.
- **subsonic migration happens on a branch.** Merging is your call, and the current harness keeps working until then.
- **Running agents from a UI** opens the user's own `claude` or `copilot` in a terminal under their own login. The tool never handles credentials. Recheck the Agent SDK terms before any public release.
- **Not building:** drag-and-drop kanban, embedded terminals, a hosted service or database, or fleets of agents launched from the UI. Earlier research in subsonic found review load, not agent speed, is the bottleneck for this kind of tool, so review screens get priority.

## Main risks

| Risk | Mitigation |
|---|---|
| Trimming prompts removes something load-bearing | M3's rule-by-rule mapping; scenario evals (tries to chain tasks, widen scope, skip verify, or edit tracking files) must behave correctly on both agents |
| Budgets are met but real usage doesn't improve | M6 measures real transcripts, and its gate comes before any UI spend |
| `ws verify` can't express manual checks (browser, device) | `acceptance` items are typed `command` or `manual`; manual items need quoted evidence, and `requires` already routes them to the foreground |
| Copilot CLI and Claude Code diverge | The fallback path is `ws brief` + `ws worktree`, usable by any agent with a shell |
| Mod API is early access (needs Claude Code ≥ 2.1.309) | The mod stays thin; web UI is the durable surface |

## Verification

1. **Unit and contract:** ported suites plus new tests; schema validation of every `snapshot` shape; a test that no project literals exist in core.
2. **End to end, no model:** a scripted fake agent drives plan → claim → verify → settle → close on fixture repos for each profile, including crash recovery, stale writes and a dirty tree.
3. **Budgets:** `ws audit context` fails CI when any role exceeds its limit.
4. **Agent behaviour:** scenario evals through `claude -p` and Copilot CLI on the sample repo.
5. **Real-world:** `ws audit usage` on subsonic before and after, reported against the pilot targets.
6. **Surfaces:** `claude plugin test` for the mod; browser checks of each web UI screen; each IDE plugin installed and exercised against a live repo.
7. **Dogfooding:** from M3 onward, this tool's own remaining milestones run as workstreams on the tool.
